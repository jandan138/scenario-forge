# GenManip 单任务 LeRobot 制作与交付指南

适用：按科学实验交付要求，为一个 GenManip 任务制作 LeRobot 数据集并交付可运行的任务包。读者为制作人员、接收人员及协助执行的 Agent。本文提供操作说明和推荐验收基线；每个任务用[交付与验收清单](templates/genmanip-task-delivery-checklist.md)记录具体范围。

依据：[飞书科学实验文档](https://aicarrier.feishu.cn/wiki/Og5Hw2fGGi8pIyk0SpBcrkGCnjf)，2026-10-19 经 CLI 核对的 revision 6749，以及本仓库[验证与交付规范](../standards/validation-and-delivery.md)。后续使用时核对飞书是否变化。本文不替代规范正文、接收仓库接口或任务本身的成功定义。

## 1. 先确定交付到什么程度

开工前填写清单中的任务、输入来源、接收仓库基线、数据划分、目标环境、交付位置和验收范围。已有明确约定可以直接记录，不必重复确认；会改变数据语义、成功条件或交付范围的未知项，应先解决再开展依赖它的工作。

区分三个来源：

| 来源 | 在本文中的含义 | 示例 |
|---|---|---|
| 飞书明确要求 | 对应外部交付内容与制作方法，记录所读版本 | 五类交付物、标准渲染和导出脚本、指定 LeRobot commit |
| 已有仓库规范 | 引用规则编号，按适用范围执行 | VAL-001 的证据分层、VAL-003 的内容与证据绑定 |
| 实践建议及任务约定 | 推荐做法及本次选择，不自动变成所有任务的硬要求 | 试制覆盖、回放数量、训练冒烟、接收数据目录 |

先明确交的是“训练数据”“可安装任务包”还是“已安装并在接收端验证的任务”。完成导出不等于完成安装；能够读取数据不等于模型训练成功。参见 [VAL-001](../standards/validation-and-delivery.md#val-001)。

## 2. 五类交付物与位置

飞书 revision 6749 的交付要求如下。前三类使用接收仓库下的标准相对路径；覆盖前核对任务范围并保留备份。

| 交付物 | 文档指定位置或方式 | 接收时检查 |
|---|---|---|
| task config YAML | `configs/tasks/scientific_experiments/`，离线覆盖到接收仓库 | 入口、case、步数、任务名和资产引用一致 |
| USD及依赖 | `saved/assets/scene_usds/scientific_experiments/`，离线覆盖 | 引用能解析；专用依赖完整；公共资产前提明确 |
| task data | `saved/tasks/scientific_experiments/`，离线覆盖 | 配置能找到正确初态、种子、指令及记录动作 |
| metric | `genmanip/extensions/metrics/scientific_experiments/`，代码提交 | 与场景属性和成功定义相符，有针对性的正反例验证 |
| LeRobot 数据集 | 标准流程制作，按任务及档次上传指定OSS目录，记录读取环境 | 数据、视频、元数据、划分及读取行为通过约定检查 |

飞书明确的接收仓库是 `/mnt/data/chenjiantong/GenManip-Sim/`。revision 6749新增LeRobot正式交付位置：`oss://pjlab-bjpai-sim/chenjiantong/scientific_experiments_data/lerobot_dataset/`，按`<task_name>_300/`和`<task_name>_500/`组织。每个目录直接包含`data/、meta/、videos/`；文档中的task_04是命名示例，不是所有任务都使用该名称。

本地制作目录、接收安装目录与OSS交付目录分别记录。此前Task09按revision6732完成的本地安装与READY保留其原范围；新要求增加OSS发布及传输/回读验收，不能将本地完成直接解释为OSS已经完成。

制作目录可以保留原始记录、中间 LMDB 和诊断；正式交付应有独立、可核验的内容。接收人使用数据集不应依赖个人临时目录。场景仍可能依赖接收方原有机器人、公共材质和 SDK，这些前提需要列明。参考 [VAL-003](../standards/validation-and-delivery.md#val-003)、[VAL-005](../standards/validation-and-delivery.md#val-005)。

## 3. 先划分，再扩展数据

**源示范**是一条原始记录；**episode**是最终数据集中的一条记录。同一源示范换十个背景形成十条 episode，并不等于十条独立采集。需要按源划分的留出协议，应在背景扩展前确定，避免同一源同时进入训练和留出集合。

制作清单至少能回答：源 ID 属于哪个集合、使用哪个背景与指令、最终对应哪个 episode、是否进入统计量。不能依靠文件夹顺序或文件名猜测这些关系。

Task09 的具体约定是：60 条源按数值 ID 排序，前30条×10背景形成300档，前50条×10背景形成500档，最后10条留出。300是500的源集合子集，但不是500目录中连续的前300条；两档独立生成索引和统计量。该选源方法是本次约定，其他任务应按自身协议确定。

`unseen` 指相对训练分布未见过的因素，不表示所有因素都未见过。Task09 的四组例子为：

| 分组 | 初态来源 | 背景 | 指令 |
|---|---|---|---|
| unseen_background | 训练已有源 | 未见 | 已有 |
| unseen_instruction | 训练已有源 | 已有 | 未见 |
| unseen_prospect | 留出源 | 已有 | 已有 |
| mixed | 留出源 | 未见 | 未见 |

本例每组十个配对 case，共40例，并非把所有因素做全组合；prospect 在该协议中也不表示新相机角度。留出十条源不意味着另交一个100条的训练集。见[划分案例](../records/2026-10-16-task09-training-split-v2.md)。

## 4. 制作顺序与每一步的检查点

| 阶段 | 怎么做、为什么 | 继续之前应有的依据 |
|---|---|---|
| 检查原始记录 | 保留不可变原件；核对完整性、源 ID、状态/动作字段、坐标系、单位和时间信息 | 来源与哈希、缺失项和任何推断/修正的说明 |
| 制作 LMDB | 按文档使用 `create_lmdb_from_json.py`；先确认目标是记录状态渲染还是动作回放 | 标准渲染 parser 能读取所需物体、机器人连杆及任务属性轨迹；字段长度与动作对应 |
| 液体缓存 | 涉及液体时按 `standalone_tools/create_liquid_surface_cache.py` 制作并检查缓存 | 缓存覆盖所需帧、可加载、与液体记录及场景版本一致；不适用时写明依据 |
| 代表样本试制 | 用标准 `render.py` 跑完整代表 episode，覆盖关键状态、背景或液体变化 | 数值对照、实际渲染、相机及日志检查通过；选择样本的理由明确 |
| 批量渲染 | 沿用已验证输入、代码、参数和划分，每个输出能够追溯来源 | 完成数量以已验收产物计数；保留失败尝试，避免重复或漏项 |
| LeRobot 导出 | 使用 `standalone_tools/genmanip2lerobot.py` 和约定版本 | 实际导出顺序、数据/视频对应关系、元数据及统计量正确 |
| 制作侧验收 | 按下一节检查数据，生成与最终内容绑定的报告 | 必做项完成；失败和未覆盖项没有被隐藏 |

**动作回放 LMDB 不一定足以渲染记录状态。** 只有控制命令和初态，不能假定包含逐帧物体位姿、连杆姿态、液体或显示属性。Task09 曾因此重做输入转换；补齐转换器及标准脚本修复应单独记录版本、差异和验证，不能写成“完全未经修改的原流程”。见[输入兼容审计](../records/2026-10-16-task09-receiver-delivery-audit.md)和[标准制作案例](../records/2026-10-16-task09-standard-pipeline-v3.md)。

文档指定 LeRobot commit 为 `2b71789e15c35418b1ccecbceb81f4a598bfd883`。还需记录实际依赖版本：Task09 使用该版本时，默认 `datasets 4.5.0` 出现读取不兼容，隔离使用 `3.6.0` 后验证通过。这是该组合的兼容经验，不是所有 LeRobot 版本的全局依赖要求。

原始采样时间未知时应保留未知状态。导出 FPS、仿真物理频率、控制命令周期和视频播放速度是不同概念；不要从其中一个倒推其他值。动作语义、状态修正及其影响按 [VAL-008](../standards/validation-and-delivery.md#val-008)记录。

## 5. 怎样验收，以及什么才算通过

下表是有案例依据的推荐基线。每次任务在清单中确定哪些是必做项、覆盖哪些样本、采用什么阈值。阈值来自接口、任务定义或有依据的约定；遇到失败先查原因，不为通过而放宽阈值。

| 验收维度 | 推荐检查与证据 | 通过条件及边界 |
|---|---|---|
| 交付完整性 | 五类清单、代码版本、资产引用、文件哈希、归档 CRC/SHA、依赖说明 | 接收内容与清单一致，必需内容可获取；目录存在或归档能打开不足以证明任务可用 |
| 划分与数量 | 源集合及 episode 映射、唯一性、各档条数/帧数、评测绑定、统计范围 | 满足本次划分；无误纳留出源、漏项或重复补数；数据顺序与映射一致 |
| 数值与语义 | 字段/形状/单位、有限值、帧对齐、episode及全局索引、时间戳、指令、与源记录对照及统计量重算 | 标准格式和约定语义均满足；标准 reader 能打开并不能替代语义检查 |
| 视频与视觉 | 各相机帧数、尺寸、编码和时序；全量解码；按关键阶段及变化因素选帧目视 | 视频完整且与记录对应；场景内容、任务关键状态可观察；解码通过不代表物理正确 |
| 接收端读取 | 在正式路径、约定环境下使用原生 reader 和 DataLoader，检查首中末、随机、跨episode及时间窗口 | 数据、图像、指令和padding行为正确；记录所测并发方式，不将单进程通过扩大到多进程 |
| 接收端运行 | 约定case的冷启动、实际初态、相机、metric加载、动作回放、完整启动/执行日志及结果视频 | 无影响执行有效性的未解决错误，动作/状态/结束原因符合协议；任务分数单独记录 |
| metric与任务成功 | 对规则做针对性的正反例检查，记录成功/失败案例及判分依据 | 是否要求全部或指定数量成功，由本次目标明确；正常回放但低分是任务失败，不能写成任务成功 |
| 训练及策略效果 | 若范围要求，验证训练入口/若干训练步或规定的策略评测 | 只声明实际做过的级别；reader、训练冒烟、收敛和策略效果互不替代 |

依据 [VAL-001](../standards/validation-and-delivery.md#val-001)、[VAL-002](../standards/validation-and-delivery.md#val-002)、[VAL-004](../standards/validation-and-delivery.md#val-004)。结果可写“通过／未通过／未执行／不适用”，后两项说明原因；未完成必做项不能算作通过。非必做项未执行也应明确，不能用空白暗示已验证。

Task09 本次约定40例独立初始化和四组各一条完整回放，不做模型训练、不要求四例满分。两条0.1分回放通过了执行与视频检查，但仍是任务失败；两条1.0分仅证明对应记录动作在该次运行达到判分条件。该任务接受单次有效4–5g读数，不要求稳定保持，最终视频帧与接受事件可能读数不同。这些都属于本例范围，不能作为其他任务降低成功要求的依据。

**READY 表示本次约定范围完成。** 回执应指向验收依据、最终清单和报告，说明是否已安装、任务成功情况和未测试项。只有导出完成，不能宣布整个任务已交付；若训练或全部case成功被列为必做，就必须完成后才能作相应声明。

## 6. 安装、交接与收尾

1. 核对接收仓库当前提交、分支、子模块和本地改动。制作期间同事可能已更新仓库，集成应保留这些工作。
2. 在候选目录准备代码与离线内容并检查；安装前记录受影响路径、原版本及备份。正式目标路径实际可写、空间可用，不能只看全盘剩余容量。
3. 数据复制后核验哈希；任务文件按约定相对路径安装。代码分支是否仅本地保存、是否推送、是否创建PR，按已明确范围执行并在交接中写清。
4. 从正式接收路径重新做约定的读取及运行验收。制作机上的成功不能直接证明接收环境成功；但相同字节、相同适用条件的证据可以明确引用，避免无理由重复制作。
5. 整理清单、报告和归档，检查最终内容与证据仍一致；变更文件后刷新受影响的证据。最后更新当前交付入口并发布验收回执。

接收 README 至少说明：交付内容与入口、环境及公共依赖、最短读取/运行方法、数据划分、代码提交、安装状态、验收范围与实际分数、已知限制、归档恢复和回退方法。若跟踪中的 YAML 通过离线覆盖交付，应解释工作区差异，避免接收人误用 `git restore` 丢弃配置。

OSS交付先核对目标前缀：存在不同内容时处理版本冲突，不对公共数据集根目录做镜像删除。若选择直接上传标准目录，先上传并核验数据、视频及其余元数据，最后写入`meta/info.json`；目录可见不等于上传完成，也不是原子发布。完成后核对全量对象名称、数量、大小及可靠校验值，缺少可靠远端校验值的对象回读计算哈希，不能仅按大小通过；再在接收环境从OSS下载的独立样本上验证原生reader。相同文件已有的全量语义/视频验收可按哈希绑定复用。发布回执记录OSS路径和检查结果，不修改既有本地交付包的READY。

只提供目录和分支名称还不够：接收人应能找到实际可用版本、判断是否需要安装，并知道哪些结果没有验证。旧产物按 [VAL-006](../standards/validation-and-delivery.md#val-006)保留，不在原交付包里追加修复冒充原版本。

## 7. 常见问题：先查什么，再怎样处理

| 现象 | 先核查 | 处理原则与案例 |
|---|---|---|
| 条数够了，但训练协议不符 | 源划分、背景扩展及统计量是否混入留出源 | 按协议重建对应档次；旧600条保留为历史，不改名冒充合格500档。[划分修订](../records/2026-10-16-task09-training-split-v2.md) |
| LMDB可以回放，但标准渲染读不了 | 是否缺逐帧物体、连杆或任务属性 | 先修复输入契约并试制，不直接扩大渲染量。[兼容审计](../records/2026-10-16-task09-receiver-delivery-audit.md) |
| 同样版本名称，接收端报接口错误 | 实际导入路径、commit、子模块和依赖版本 | 核实运行的是哪份包，用有验证的隔离环境或匹配源码；保留差异说明。[接收案例](../records/2026-10-19-task09-receiver-installation.md) |
| 磁盘显示有空间，却写入失败 | 实际目标目录的写入、配额/后端限制和其他挂载子树 | 不把猜测当原因；已完成数据保留，迁移新写入位置并更新唯一当前入口。[存储恢复](../records/2026-10-17-task09-storage-recovery.md) |
| 主机失联或导出中断 | 已提交元数据与半成品边界、旧进程是否可能仍写入 | 未知旧写入者状态时用独立候选副本；验证续导等价性及前缀不变，再继续。不能只按视频个数续编号。[导出恢复](../records/2026-10-18-task09-export-recovery.md) |
| GPU空闲，看起来“停了” | 当前是渲染、CPU编码、校验还是已经结束；产物和日志是否推进 | 根据当前阶段判断进度。持久会话不能保证主机故障后仍运行；ETA依据实测吞吐并分阶段给出。[导出恢复](../records/2026-10-18-task09-export-recovery.md) |
| SDK启动长时间无进展 | 是否进入场景、原始日志、资源占用及本次拥有的进程 | 保留失败尝试，明确基础设施问题后做有限的同输入重试；不能把任务低分当启动失败反复重试。[接收案例](../records/2026-10-19-task09-receiver-installation.md) |
| 新增机器/卡后担心重复或漏任务 | 输入/代码身份、任务分配、输出归属、GPU/端口/缓存隔离 | 先验证新节点；按已验收产物核对总量，不把运行中任务再次分配给另一节点。[六卡案例](../records/2026-10-17-task09-six-gpu-render.md) |
| 旧状态和新状态互相矛盾 | 当前入口指向哪次制作/交付，更新时间及对应证据 | 通用指南写方法，当前入口写有效版本，日期记录写历史；不凭“final”目录名认定完成 |

这些案例解释诊断与恢复的思路；其中的 IP、端口、超时秒数、GPU设置和缓存路径均需在实际环境核实，不能直接推广为通用配置。

## 8. 验收标准以后怎样迭代

每次交付保留当时的飞书版本、仓库规范 Git 版本、本任务验收约定及对应报告。规范版本沿用仓库 Git 历史，不另维护一套平行的手工版本体系。

增加训练冒烟、扩大回放覆盖或提高成功要求时，写明变化、依据、适用任务、对已有交付的影响，以及需要补验的内容。已有通过证据只在内容和适用范围仍匹配时沿用；新标准不能自动使旧包获得新资格，也不默默撤销其原范围的结果。按[规范维护流程](../standards/maintenance.md)处理，有通用依据的规则才进入 standards，尚未验证的想法保留为待验证建议。

新要求若暴露已有必做项的实质缺陷，应重新判断该范围的交付结论，不能仅标“旧版本”而忽略。补验或修复另留记录，必要时形成新交付版本。
