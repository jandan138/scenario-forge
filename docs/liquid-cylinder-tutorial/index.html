01先找准病因

它看起来像杯子，物理上却不一定是杯子

视觉模型只负责“像不像量筒”；液体碰撞模型负责“能不能把粒子留在里面”。原资产是适合渲染的开边薄壳，直接交给 GPU 做凸分解时，内腔无法得到稳定表达。

VISIBLE MESH

眼睛看到的是对的

透明筒壁、刻度、底座都正常，尺寸也没有错。它不该因为物理问题被替换或改粗。

COLLISION MESH

GPU 摸到的是错的

薄面、开口边和不稳定的分解结果，会让粒子穿壁、从底部漏出，甚至触发 GPU cooking 错误。

LIVE READBACK

旧证据读错了状态

simulationPoints 是写入的初值；真正判断是否漏液必须读运行中的 points。

纠错证据：改用实时 points 后，旧量筒三次只留下 43–45 / 548 粒。问题不是“液体颜色太淡”，而是碰撞容器根本没有成立。
02五轮修复历程

真正的突破，不是把参数越调越大

这只量筒经历了两条失败路线、一次证据纠错，最后才回到 0812 已验证的容器拓扑。把过程保留下来很重要：它告诉我们何时应继续查参数，何时必须停止调参并重做几何。

先分清三件事

闭合只说明网格没有洞；GPU 可烹饪说明 PhysX 能把它变成 GPU 可处理的碰撞组成；能装液还要靠运行时实时粒子验证。三者不能互相代替。

最终判断

原量筒的问题来自“高而薄、开边、视觉面片密集”的拓扑。0812 烧杯能工作，是因为它使用了简单、封闭、明确保留内腔的专用碰撞拓扑。

STAGE 01原始资产

把视觉薄壳直接当容器

384 个点 · 288 个四边形 · 192 条边界边

网格适合透明渲染，却有大量开口边。GPU 凸分解无法稳定得到既有筒壁、又保留内腔的碰撞结构。

结论：这是几何前提不成立，不应先调 rest offset。
STAGE 02 · r8.1失败

给视觉筒壁加分区

p12 / p24 / p48：每次冷启动只更新 1 帧后超时

分区越密，GPU cooking 与接触计算越不稳定。关闭这些分区的负对照反而连续通过 5 次更新。

结论：更多分片不等于更好的 GPU 容器。
STAGE 03 · r8.2仍失败

补双层环口，让薄壳闭合

新增 96 个环口面 · 58 / 548 留存 · 548 / 548 洒出

网格成为 closed manifold，中央杯口也保留了，但仍无法成为合格的 GPU-PBD 容器。静态保液率只有 10.58%。

结论：拓扑闭合是必要条件，却不是充分条件。
STAGE 04证据纠错

发现我们读错了粒子状态

旧：simulationPoints　新：points = 43–45 / 548

simulationPoints 只是写入的初值，不能证明粒子还在杯中。改读运行中的 points 后，旧“通过”结论被撤销。

结论：验证管线也可能错；错误证据必须公开作废。
STAGE 05 · FINAL通过

把 0812 容器拓扑变形到量筒尺寸

50 个点 · 96 个三角面 · 边界 0 · 非流形 0

视觉 mesh 完全不动，只增加一个隐藏闭合碰撞 mesh：内腔半径 16.5 mm、底面 16 mm、杯口高度 278.24 mm。

实时 points：至少 546 / 548；87–88 FPS。

为什么 0812 烧杯能跑？

它的液体碰撞层本来就是低复杂度、封闭、带明确内腔的专用网格。GPU 看到的是一只“物理杯子”，而不是透明视觉表皮。

为什么原量筒不行？

量筒又高又窄，视觉模型是开边薄壳；直接凸分解容易封住杯口、丢失内腔或退化为不稳定的碰撞组成。

一句话：拓扑不同，不是少调了一个 PhysX 参数。正确迁移方式是复用 0812 的容器拓扑经验，再按源量筒尺寸做可追溯变形，而不是照抄一个固定碰撞体。
03重建隐形内胆

外观不动，只重做液体真正接触的那一层

我们没有拿圆柱体粗暴套住量筒，也没有修改原始视觉 mesh。ConvertAsset 参考已经跑通的 LabUtopia 0812 容器拓扑，把模板按量筒的实测半径和高度变形，生成一个source-derived、封闭、可三角化的隐藏碰撞网格。

为什么这不是“一个实心 GPU 凸包”？
入口只有一个隐藏 mesh prim，但 convexDecomposition 会把它烹饪为若干可由 GPU 处理的凸组成部分，从而共同表达杯壁和中空内腔。若直接把整个量筒做成单一 convex hull，杯口会被封住，液体反而进不去也倒不出。
04让初值和容器对齐

粒子参数不乱改，先让它们站在正确的位置

最终方案沿用 0812 已验证的轻量液体参数，只把外观调成更易观察的蓝色。真正解决“刚抬量筒就冒出一坨液体”的关键，是先让量筒在 755 mm 桌面上自然落稳，再把预沉降粒子保存到量筒的局部坐标中。

07照着复现

把这套方法迁移到下一个容器

不要复制量筒的固定尺寸；复制的是工作方法：先拓扑、再静态保液、再规定轨迹、再打包、最后跑机器人。

你看到的现象先查什么应该往哪条线修
GPU cooking 失败

边界边、非流形边、薄面与凸分解结果。

重做简洁封闭拓扑；不要先调 offset。

烹饪通过，但仍漏液

读取实时 points；检查初始穿插与 self-collision。

先修证据与初态，再判断是否需要改几何。

静态保液通过，但装液初始状态漂移

容器支撑姿态、粒子局部坐标和共同场景变换。

修统一坐标映射；不要分别给容器和液体加高度补偿。

液体稳定，但夹爪打滑

抓取高度、夹爪接触、抬升速度和控制轨迹。

进入机器人控制线；不要回头改已通过的容器碰撞体。

五件不要做的事

  • 不要先靠增大 rest offset 救一个开边薄壳。
  • 不要把单一实心 convex hull 当作中空容器。
  • 不要读取 simulationPoints 冒充实时保液结果。
  • 不要分别修正容器高度和粒子高度。
  • 不要在 Scenario Forge 或 GenManip 写量筒专用物理补丁。
